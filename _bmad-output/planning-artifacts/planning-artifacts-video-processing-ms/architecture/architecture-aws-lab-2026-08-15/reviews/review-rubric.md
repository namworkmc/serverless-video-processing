## Findings

### CRITICAL

### HIGH

#### F-1 — `videoId` provenance contradicts the frozen spec (line 105 vs spec lines 25/38/58)

- **Location:** Consistency Conventions, "Data & formats" row, line 105: *"`videoId` is a UUID generated at ingress (`upload-service`)."*
- **Problem:** The frozen story-1 spec pins `CreateVideo(title, bucket, originalKey, contentType, sizeBytes)` with **no `video_id` input** and "generated UUID `video_id`" produced by metadata-service (spec I/O matrix line 38, rpc signature line 50, `VideoMetadataGrpcService` line 58). If a builder follows the spine, upload-service generates the UUID — but it cannot pass it through `CreateVideo`, and AD-2 (line 51) says metadata-service is the sole mutator/owner of the video record. Three documents disagree on who owns identity.
- **Risk:** Story 2 (upload-service) either violates the frozen `CreateVideo` contract or silently renegotiates id generation, producing a different record-identity scheme than story 1.
- **Fix:** Change line 105 to: *"`videoId` is a UUID generated by `metadata-service` on `CreateVideo` (source of truth, per AD-2)."* If identity is meant to be client/ingress-supplied, that is a human renegotiation of the frozen spec — flag it as such, don't paper over it.

#### F-2 — AD-2's "no shared storage between services" is unenforceable and self-contradicts the seed (line 51 vs lines 138–143, 75)

- **Location:** AD-2 Rule, line 51: *"no shared storage between services; no reading another service's store."* Prevents-clause line 50: *"shared storage being read/written from two codebases."*
- **Problem:** The Structural Seed (lines 138–142) has **both** upload-service (`putObject` to `video-uploads`) and processing-service (`get/putObject` on the same buckets) touching S3 — shared storage read and written from two codebases, which is exactly what AD-2 claims to prevent. AD-6 (line 75) then configures that S3 access. The rule as written cannot be enforced without contradicting the seed; a reviewer following it literally would block processing-service from reading the uploads bucket.
- **Risk:** Either the seed is silently violated (AD-2 becomes decoration) or a later reviewer mis-blocks legitimate S3 flow. The stated intent (one record store per service) is right; the wording is wrong.
- **Fix:** Scope AD-2 to *record/stateful stores*: *"no shared record store (DB, index, notification history) between services; no service reads another service's record store. S3 is content-addressed object storage: `upload-service` owns writes to `video-uploads`, `processing-service` reads it and owns writes to the processed bucket; object ownership = who writes."* Optionally list which service may read which bucket.

### MEDIUM

#### F-3 — Operations/environment envelope: CI/CD and the environment list are wholly silent (whole spine)

- **Location:** Entire document; the "Deployment | 1 Dockerfile per service" row (line 131), the docker-compose seed (line 160), and Deferred (lines 195–204) cover deployment and infra/provider, and observability is deferred (line 203) — but **no CI/CD decision exists anywhere** (not decided, not deferred, not open-questioned).
- **Problem:** The rubric explicitly calls the operational/environmental envelope. The spine owns it at initiative altitude. There is no statement of how/whether the 5 services get built, tested, and run in CI (e.g., `mvn package` gate, ministack-backed integration tests, image publish, where a pipeline would run). "Dev" is the only named environment; the port table is explicitly dev-only (line 108) and real-AWS is deferred, but the transition trigger and environment inventory are unstated.
- **Fix:** Add one line to Deferred: *"CI/CD — no pipeline decision until all 5 services exist; verification is `mvn -q -DskipTests package` + compose-up smoke tests. Revisit when the infra phase starts."* If a pipeline is wanted now, decide it instead.

#### F-4 — Logging is listed as a governed concern but no convention is given (line 106, line 203)

- **Location:** Conventions line 106 row heading: *"State & cross-cutting (mutation, errors, logging, config)"* — the convention cell governs mutation/errors/config but is **silent on logging**. Deferred line 203 pushes observability to later.
- **Problem:** The concern is declared but not decided. Each of the 5 services will invent its own log format/levels/headers; the deferred observability push then reconciles five formats. This is a per-unit divergence the spine nominally covers but leaves open.
- **Fix (minimal):** Add to the row: *"logging = Spring Boot defaults (logback, INFO, `com.videolab` loggers); structured/JSON logging deferred with observability."* Or explicitly open-question it.

#### F-5 — Client-facing HTTP facade contract (paths, shapes, SSE framing) is ungoverned (AD-7 line 81, capability map lines 187–193)

- **Location:** AD-7 fixes only the error envelope (`{"error": ...}`). AD-1's boundary row (line 45) says "HTTP controller and/or @GrpcService" with no facade convention. The seed shows upload (multipart POST, 8080), notification (SSE, 8082) and search (HTTP + gRPC, 8091) all facing the same client.
- **Problem:** These are real cross-unit divergence points the spine misses. Three services will each invent REST resource naming, request/response DTO shapes, and SSE event framing; the client integrates against all three. The spine gives a builder nothing to read for HTTP beyond error shape.
- **Fix:** Add a convention or fold into AD-1/AD-7: *"HTTP facades: resource-noun paths (`/videos`, `/search/videos`, SSE `/stream`), response DTOs live in `video-common`, SSE event `event:` = the event name (`video.processed`)."* If facade shape is deliberately per-service, say so explicitly and defer with an open question.

#### F-7 — Spring Cloud AWS 4.1.0 pairing with Boot 4.1.0 is unverified, and SCAWS 4.x dropped RDS support (lines 124, 128)

- **Location:** Stack: "Spring Cloud AWS | 4.1.0 (BOM import)" (line 124) paired with Boot 4.1.0; "metadata-service DB | H2 file (dev) — JPA abstracts future RDS" (line 128).
- **Problem (a):** The canonical awspring.io compatibility table lists SCAWS **4.x ↔ Spring Boot 4.0.x / Spring Cloud 2025.1.x**; SCAWS 4.1.0 shipped 2026-07-22 (after Boot 4.1.0's 2026-06-10 GA) and is plausibly retargeted, but the published matrix does not yet say 4.1.0 ↔ Boot 4.1.0. This pairing must be confirmed (or a note added that it was verified at pin time) — otherwise the BOM import may drag incompatible dependency management.
- **Problem (b):** SCAWS 4.x removed RDS auto-configuration (RDS is only in 2.x/3.x). The "JPA abstracts future RDS" claim is true only if RDS wiring goes through Spring Boot's `spring.datasource.*`, not SCAWS. As written, a later infra story could assume SCAWS RDS support that does not exist in 4.x.
- **Fix:** Verify/pin the SCAWS↔Boot pairing at first build and record it. Amend line 128: *"future RDS via Spring Boot `spring.datasource.*` (SCAWS 4.x does not auto-configure RDS)."*

### LOW

#### F-6 — Event DTO schema evolution is ungoverned; AD-5 scopes only the `.proto` (line 65–69)

- **Location:** AD-5 binds "`video-common` `.proto`" only. `VideoUploadedEvent`/`VideoProcessedEvent` (JSON, SQS) are also in video-common (namespace map line 35).
- **Problem:** AD-5's additive-only rule and version-coexistence rule have no stated counterpart for the event DTOs. Today all modules compile against one jar so a breaking event change is compile-coupled (caught early) — but the "coexist until consumers migrate" guarantee, which matters for separate deploys in the real-AWS future, is unstated for events.
- **Fix (cheap):** One sentence in AD-5: *"the additive-only rule extends to the JSON event DTOs."* — or explicitly defer event versioning.

#### F-8 — "spring-grpc core" naming is stale (line 125)

- **Location:** Stack: "Spring gRPC (spring-grpc core) | 1.1.0 (Boot-managed)".
- **Problem:** In the 1.0.x line, `org.springframework.grpc:spring-grpc-core` carried the autoconfiguration; in 1.1.0 that autoconfig migrated **into Spring Boot 4.1** and the official entry points are the Boot starters `spring-boot-starter-grpc-server` / `spring-boot-starter-grpc-client` (which the spec already uses correctly, spec line 24). The Stack row points builders at a stale artifact name.
- **Fix:** Rename the row: *"Spring gRPC | 1.1.0 via `spring-boot-starter-grpc-server` / `spring-boot-starter-grpc-client` (Boot 4.1-managed)".*

#### F-9 — Outbox deferral is accepted but has no recovery path; divergence becomes permanent (line 198)

- **Location:** Deferred: *"Transactional outbox … Accepted as eventually-consistent for the lab; revisit if divergence is observed."*
- **Problem:** The accepted risk is that a status commit (metadata) and an SQS publish can disagree — a lost event leaves search index / notification history permanently missing that video. AD-4 prevents duplicates, not losses. Since both derived stores are "disposable/rebuildable" (AD-2), a one-line recovery affordance converts "permanent divergence" into "recoverable".
- **Fix:** Append to the deferred item: *"Recovery: derived stores are rebuildable from `metadata-service.ListVideos` (search) and by re-consuming retained events (notification)."* Keep it a discuss/defer flag — this is an acceptable lab trade, just not an open loop.

#### F-10 — Dockerfile convention doesn't pin a shared base; content is deferred to stories (line 131, line 204)

- **Location:** Stack line 131 (multi-stage maven → JRE, 1 Dockerfile per service); Deferred line 204 (ffmpeg install left to the Dockerfile story).
- **Problem:** The packaging *pattern* is decided but the per-service Dockerfile content (base image tag, JRE 21, healthchecks, exposed ports) is not; 5 stories will each write a Dockerfile and can diverge. ffmpeg is legitimately deferred, but the shared skeleton should not be.
- **Fix:** Pin the base now (e.g., *"all service images: `eclipse-temurin:21-jre-*` base, expose only the ports in the port table, actuator healthcheck"*) and leave only the ffmpeg layer to the Dockerfile story.
