### F1 — CRITICAL — Binary video uploads are rejected or silently corrupted through the gateway
**Disposition: fix-now (before Epic 2) OR formally accept as lab limitation + reconcile spec — human decides.**

The epic's headline journey (FR-1: "a client uploads a video file") does not survive real video bytes. Live probes against the running gateway this run:

| Probe | Payload | Result |
|---|---|---|
| Happy text-safe upload | ASCII text as `.mp4` | 200 + S3 object + UPLOADED record + event (works) |
| Synthetic MP4 (1 KB, contains bytes `0x80–0xFF`) | real high-byte content | **400** `"request body contains undecodable characters"` |
| 2 KB `/dev/urandom` | random binary | **400** same |
| 6 raw bytes `00 01 02 ff fe fd` | invalid UTF-8 | **400** same |
| 8 bytes `c3 a9 c3 a9 c3 a9 c3 a9` (valid UTF-8 `éééé`) | valid multibyte | **200 — but stored bytes are `e9 e9 e9 e9` (4 bytes): silent corruption, 8→4** |
| Direct Lambda invoke, body = raw bytes decoded latin-1 | same binary | **200, correct** |

- **Source:** live behavior probes (this retro, 2026-08-20); `lambdas/upload_handler/handler.py:109-119` (latin-1 round-trip); `lambdas/upload_handler/tests/test_upload_handler.py:118-119` (helper encodes file bytes latin-1, mirroring the same premise) and `:556-565` (`test_non_latin1_body_returns_400` encodes the premise as an assertion); `README.md:85-86` (`sample.mp4` is an ASCII text stub).
- **Root cause (leading hypothesis, grounded in the byte evidence):** floci's API GW v2 embeds the multipart body in the Lambda event JSON as a **UTF-8-decoded string**, not raw bytes — contradicting the spike's "multipart delivered RAW" claim for any non-ASCII content. Bytes forming valid UTF-8 are decoded to their characters and cannot round-trip back to the original bytes via latin-1 (2 bytes → 1); bytes that are not valid UTF-8 are mangled so the handler's `body.encode("latin-1")` raises → 400. The handler's latin-1 logic is **sound given a faithful string** (proven by the direct invoke) — the transport, not the parser, loses the bytes.
- **Verification gap that let it ship:** every unit test uses fakes (`FakeS3Client`/`FakeTable`/`FakeEventBridgeClient`) with latin-1/ASCII bodies; the Story 1.3 live verification and the Bruno collection both use the ASCII text stub. **No test or live check ever exercised real binary bytes through the actual multipart path**, so FR-1 was never verified with actual video content. Passing tests did not substitute for running real bytes through the system.
- **Why it matters downstream:** Epic 2's transcode consumes the uploaded object. If real uploads are corrupted or absent, the processing leg operates on garbage. This should be resolved (or formally accepted as a documented lab limitation) before/within Epic 2.

## Open questions

- ~~**Is F1 a floci bug or a contract misunderstanding?**~~ **RESOLVED by the AI-1 spike (2026-08-20, same session):** it is a floci 1.6.0 bug, already fixed upstream in **floci 1.7.0** (released 2026-08-18).
  - **Root cause (confirmed in floci source):** `ApiGatewayExecuteController.java:783` builds the Lambda proxy event with `event.put("body", new String(body))` — Java's platform-default (UTF-8) charset decode of the raw request bytes. Bytes forming valid UTF-8 collapse to their characters (cannot round-trip back to the original bytes); invalid-UTF-8 bytes become U+FFFD, which the handler's `latin-1` encode then rejects as 400. The spike's "multipart delivered RAW" claim was only true for ASCII.
  - **Upstream fix:** floci 1.7.0 changelog — `apigatewayv2: encode binary Lambda request bodies (#2203)`. Non-text content types (`multipart/form-data` is not in the text set) are now delivered base64-encoded with `isBase64Encoded: true` — matching real AWS HTTP API behavior.
  - **Spike proof:** isolated floci 1.7.0 on :4567, echo Lambda + HTTP API, 1164-byte binary multipart (all 256 byte values) → `isBase64Encoded: true`, **FULL ROUND-TRIP MATCH**. 1.7.0 changelog is bug-fixes-only; nothing touching S3/DynamoDB/EventBridge/Lambda/SFN used by this stack. Spike container and artifacts removed after the run.
  - **Remediation path (for the dev loop, per AI-1):** bump `docker-compose.yaml` to `floci/floci:1.7.0`; change the handler's base64 branch from reject to `base64.b64decode` (the AWS-correct path, currently mis-coded as a 400 at `handler.py:103-107`); add a binary-payload test; re-verify the upload journey with real video bytes. Note: this supersedes the "never assume base64" guidance in the Story 1.3 spec/AGENTS.md pitfalls — that guidance was a 1.6.0 artifact.
- **Should the Bruno collection carry a real (small) binary MP4** once the fix lands, so FR-1 is continuously verified with actual video bytes? (Recommendation: yes.)
